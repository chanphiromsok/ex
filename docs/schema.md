# Table design (v1) and how it maps to Ash

`docs/schema.sql` is a **preview**, not a migration. The real tables are generated by AshPostgres (`mix ash.codegen`) from the resources below, so every convention here follows Ash. All tables are in the existing `Ex.Repo`; resources live in new domains next to `Ex.Accounts` and are exposed through the existing `/api/json` router.

## Conventions (what Ash generates)

| Topic | Ash resource | Column / table |
|---|---|---|
| Primary key | `uuid_primary_key :id` | `uuid DEFAULT gen_random_uuid()` |
| Timestamps | `create_timestamp :inserted_at` (and `update_timestamp :updated_at` only on editable tables) | `timestamp(6)` UTC, default `now() AT TIME ZONE 'utc'` |
| Foreign keys | `belongs_to :created_by, Ex.Accounts.User` | `created_by_id uuid REFERENCES users` |
| Enums | `Ash.Type.Enum` module per enum | plain `text`; allowed values enforced by `check_constraints` in the resource |
| Money | `AshMoney.Types.Money` (KHR, `constraints: [...]`) | `money_with_currency`; whole-riel and positive-amount rules as `check_constraints` using `is_whole_khr()` |
| Invoice Number | `attribute :invoice_no, :integer, generated?: true, writable?: false, allow_nil?: false` + identity | `bigserial UNIQUE` (own sequence) |
| Idempotency | `identity :unique_idempotency_key, [:idempotency_key]` + `create ... upsert? true, upsert_identity: ...` | `uuid UNIQUE NOT NULL` |
| Singleton settings | `identity :singleton, [:singleton]` on a constant `true` attribute | one row |
| Phone format | `check_constraints` + one `Ex.Phone` normalising function used by the changes | CHECK `~ '^855[1-9][0-9]{7,8}$'` |
| Partial unique indexes | `identity ... , where: expr(...)` with `identity_wheres_to_sql` | `status_events_once_idx`, `payments_one_refund_idx` |
| Triggers and `is_whole_khr()` | `postgres do custom_statements do statement ... end end` | `reject_change()` triggers (ADR-0005) |
| Current status | `first :status, :status_events, :status, sort: [seq: :desc]` aggregate on Shipment (never stored) | none |
| Balance | `sum` aggregate over Payments (KHR) | none |

## Append-only and immutable resources

An Ash resource that defines only `create` and `read` actions cannot be updated or deleted through Ash, so the rule is enforced in two places: no `update`/`destroy` action in the resource, and the `reject_change()` trigger in Postgres (ADR-0005).

- Append-only: `payments`, `status_events`, `notes`, `receiver_corrections`, `price_changes`, `station_setting_changes`, `user_assignment_changes`.
- Written once in the create transaction: `shipments`, `parcels`, `shipment_sale_items`.
- Resolvable with a guarded update action (decide/resolve columns only, once): `incidents`, `cancellation_requests`.

## Tables

Reference data: `locations`, `stations`, `routes`, `size_classes`, `sale_items`, `pricing_settings` (price_per_kg, cancellation_fee_percent, cancellation_fee_cap), `station_settings`.
People: `users` (role, station_id; existing AshAuthentication resource extended).
Shipment: `shipments`, `parcels`, `shipment_sale_items`, `payments`, `status_events` (seq per Shipment), `notes`, `receiver_corrections`, `incidents`, `cancellation_requests`.
History: `price_changes` (price_per_kg, size_class, sale_item, cancellation_fee), `station_setting_changes`, `user_assignment_changes`.

Every pricing, setting and role change is written as a history row by an Ash change in the same transaction as the update, so "current" equals the table value and the log never drifts.

## Creating a Shipment in Ash

One `create :create` action on Shipment with `manage_relationship` for Parcels, Sale Item lines and the first Payment, wrapped in the action's transaction. The change computes prices from the reference tables, rounds weight × price to whole riel, checks the Payments equal the Shipment Total exactly, and inserts the `received` Status Event with `seq` 1. Policies (`Ash.Policy.Authorizer`) restrict Staff to their own Station and Admin to read-only reference data.
